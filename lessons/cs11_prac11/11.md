# Remembering Answers with Caching

:::goal What you will be able to do

The Fibonacci numbers are defined recursively: `fib(n)` is `fib(n - 1) + fib(n - 2)`, with `fib(0) = 0` and `fib(1) = 1`. The code is short, but it computes the same values again and again.

:::try t-calls
Run it. The global counter records how many times `fib` was called. Try `fib(20)` and `fib(25)`.

```python starter
calls = 0

def fib(n):
    global calls
    calls += 1
    return n if n <= 1 else fib(n - 1) + fib(n - 2)

print(fib(10), calls)
```
:::

Computing `fib(10)` takes 177 calls. For `fib(40)` it is more than 300 million calls, and for `fib(90)` it would take longer than your lifetime. Most of those calls compute values that were already computed.

:::explain
The recursion tree contains the same subproblems many times. The cure is to **remember** each answer the first time (this is called **memoization**) and reuse it.

The simplest memory is a dict from the argument to the answer. Check it before computing, and fill it after.

::::fill f-memo
```python
memo = {}

def fib(n):
    if n [[in]] memo:
        return memo[n]
    result = n if n <= 1 else fib(n - 1) + fib(n - 2)
    memo[ [[n]] ] = result
    return result

print(fib(50))
```
:::hint
Which operator asks whether a key is in a dict?
:::
:::hint
The answer is stored under the key `n`.
:::
:::explain
`n in memo` is the quick check. After computing the answer, we store it under `n` so that every later call with the same `n` returns at once.
:::
::::

Look closely at the fill above: the answer is stored **before** we return it. Forgetting that line gives the same slow function.

::::exercise ex-fibmemo kind=write
Write `fib(n)` using a dict as memory (a global `memo` dict is fine). It must handle `n` up to 300 quickly, and `fib(0) = 0`, `fib(1) = 1`.

```python starter
def fib(n):
    return n if n <= 1 else fib(n - 1) + fib(n - 2)
```
```python tests
def ref(n):
    x, y = 0, 1
    for _ in range(n):
        x, y = y, x + y
    return x
check(lambda: fib(0), 0, "fib(0)")
check(lambda: fib(1), 1, "fib(1)")
check(lambda: fib(10), 55, "fib(10)")
check(lambda: fib(50), 12586269025, "fib(50) is instant")
check(lambda: fib(300), ref(300), "fib(300)")
```
```python solution
memo = {}

def fib(n):
    if n in memo:
        return memo[n]
    result = n if n <= 1 else fib(n - 1) + fib(n - 2)
    memo[n] = result
    return result
```
:::hint
Make a dict outside the function: `memo = {}`.
:::
:::hint
First line of `fib`: if `n` is already in `memo`, return `memo[n]`.
:::
:::hint
Compute the result, store it with `memo[n] = result`, then return it.
:::
:::explain
Now each value is computed once, so the work is about `n` calls instead of billions. The dict is the function's memory.
:::

Python can do all of that for you. `@cache` from `functools` wraps a function with a memory of its previous calls.

:::try t-cache
Run it. The second call of `square(3)` does not run the function body.

```python starter
from functools import cache

@cache
def square(n):
    print('computing', n)
    return n * n

print(square(3))
print(square(3))
print(square(4))
```
:::

Decorators can be **stacked**. The one written **closest to the function** is applied first; the one above wraps that result. Compare the two orders:

::::predict p-stack
What does this print?

```python
from functools import cache

def trace(f):
    def wrapper(n):
        result = f(n)
        print(f.__name__, n, '=', result)
        return result
    return wrapper

@cache
@trace
def a(n):
    return n * n

@trace
@cache
def b(n):
    return n * n

a(2)
a(2)
b(2)
b(2)
```
```text answer
a 2 = 4
b 2 = 4
b 2 = 4
```
:::hint
For `a`, the cache is on the outside. A cache hit never reaches `trace`.
:::
:::hint
For `b`, `trace` is on the outside, so it runs on **every** call.
:::
:::explain
`@cache @trace`: the cache checks its memory first, so `trace` only runs when the answer is new. That is why the Print After Return examples with `@cache` print each value once. `@trace @cache`: `trace` wraps the cached function, so it prints on every call, even cache hits.
:::

Time to write the memory yourself. A **memoize** decorator keeps a dict in its closure. The key is the tuple `args`, and it works for any number of arguments.

::::exercise ex-memoize kind=write
Write the decorator `memoize(f)`. The decorated function returns what `f` returns, but `f` runs only the **first** time for each tuple of arguments.

```python starter
def memoize(f):
    def wrapper(*args):
        return f(*args)
    return wrapper
```
```python tests
log = []

@memoize
def slow_square(n):
    log.append(n)
    return n * n

check(lambda: slow_square(4), 16, "first call")
check(lambda: slow_square(4), 16, "second call, same answer")
check(lambda: log, [4], "computed only once")
check(lambda: slow_square(5), 25, "a new argument")
check(lambda: log, [4, 5], "and now computed twice in total")

log2 = []

@memoize
def sub(a, b):
    log2.append((a, b))
    return a - b

check(lambda: (sub(5, 2), sub(2, 5), sub(5, 2)), (3, -3, 3), "argument order matters")
check(lambda: log2, [(5, 2), (2, 5)], "two different argument tuples")

@memoize
def fib(n):
    return n if n <= 1 else fib(n - 1) + fib(n - 2)

check(lambda: fib(90), 2880067194370816120, "fib(90) is instant")
```
```python solution
def memoize(f):
    seen = {}
    def wrapper(*args):
        if args not in seen:
            seen[args] = f(*args)
        return seen[args]
    return wrapper
```
:::hint
Create the dict inside `memoize`, outside `wrapper`, so it survives between calls.
:::
:::hint
The key is `args` itself, which is already a tuple.
:::
:::hint
`if args not in seen: seen[args] = f(*args)` and then `return seen[args]`.
:::
:::explain
This is a closure from the queue lesson combined with a decorator from the decorator lesson. Because `fib` calls its own name, which is now the wrapper, the recursive calls use the memory too.
:::

Caching also solves counting problems on grids. Suppose you stand at the top-left of a grid. You may move only **right** or **down**, and `#` cells are walls. How many different paths lead to the bottom-right cell?

Let `p(i, j)` be the number of paths from `(i, j)` to the bottom-right cell. Then:

- a wall, or a cell outside the grid, has 0 paths;
- the bottom-right cell has exactly 1 path (stay there);
- any other cell has `p(i + 1, j) + p(i, j + 1)`.

The same `p(i, j)` is needed from many places, so we cache it.

::::quiz q-inner
`p` needs the `grid`. A clean way is to define `p` **inside** `path_count(grid)` and decorate it with `@cache` there. What goes wrong if `p` is a global function decorated with `@cache` that reads a global `grid`?

- [ ] Nothing, it works the same
- [x] A later call with a different grid would reuse answers cached for the earlier grid, which are wrong
- [ ] `@cache` cannot be used on global functions
:::hint
The cache key is only `(i, j)`. Is the grid part of the key?
:::
:::hint
Think about calling `path_count` on two different grids one after another.
:::
:::explain
A cache remembers answers for its keys forever. If the grid is not part of the key, answers for grid A would be returned for grid B. Defining `p` inside `path_count` creates a fresh cache for every call.
:::

```python tests
from math import comb

check(lambda: path_count(('.....', '..#..', '.....')), 6, "the sample grid")
check(lambda: path_count(('.',)), 1, "a single cell")
check(lambda: path_count(('#',)), 0, "a single wall")
check(lambda: path_count(('..', '..')), 2, "2 by 2")
check(lambda: path_count(('...', '...', '...')), 6, "3 by 3")
check(lambda: path_count(('.#', '#.')), 0, "walls block everything")
check(lambda: path_count(('#.', '..')), 0, "wall at the start")
check(lambda: path_count(('..', '.#')), 0, "wall at the end")
check(lambda: path_count(tuple('.' * 30 for _ in range(30))), comb(58, 29), "30 by 30, needs the cache")
check(lambda: path_count(tuple('.' * 60 for _ in range(60))), comb(118, 59), "60 by 60")
check(uses('FunctionDef', 'Return'), True, "uses functions")
```
```python solution
from functools import cache

def path_count(grid):
    r = len(grid)
    c = len(grid[0])

    def get(i, j):
        return grid[i][j] if 0 <= i < r and 0 <= j < c else '#'

    @cache
    def p(i, j):
        if get(i, j) == '#':
            return 0
        if (i, j) == (r - 1, c - 1):
            return 1
        return p(i + 1, j) + p(i, j + 1)

    return p(0, 0)
```
:::hint
Define `get(i, j)` that answers `'#'` outside the grid, so walls and edges are handled together.
:::
:::hint
Inside `p`: wall gives 0, bottom-right gives 1, otherwise add the answers for moving down and right.
:::
:::hint
Put `@cache` above `def p`, and return `p(0, 0)`.
:::
:::explain
Checking for a wall comes first, so a wall at the end gives 0, not 1. The inner function reads `grid`, `r` and `c` from `path_count`: a closure. Every call of `path_count` has its own cache. Without the cache a 30 by 30 grid would need more than 10^16 steps.
:::

:::recap
- Naive recursion that revisits the same arguments can take astronomically long.
- Memoization means: look in a dict first, and store the answer before returning it.
- `@functools.cache` does this for you, but all arguments must be hashable (immutable).
- Stacked decorators apply from the closest one outwards: `@cache @trace` prints each value once, `@trace @cache` prints every call.
- Define the cached helper inside the function that owns the data, so every call gets a fresh cache.
- Counting right/down paths: wall gives 0, goal gives 1, otherwise add the two neighbours.
:::
